# Compiler-derived coordination boundaries: Rust and Go

Research for [Research compiler-derived coordination boundaries for Rust and Go](https://github.com/danielrispler/Falinks/issues/16), 2026-10-02. First-party documentation and source inspection only; no executable probe, integration selection, behavioral-correctness claim, or real-agent trial. Source pins below are **evidence snapshots**, not newest-version claims, installed versions, or a validated compatibility bundle. Vocabulary follows root `CONTEXT.md`.

**Finding:** supported interfaces provide resolved symbols and useful dependency evidence. Neither ordinary LSP navigation nor either inspected toolchain supplies a ready-made, exhaustive, revision-bound symbol coordination graph. Narrow acceptance therefore remains unproven. This is an inference from the API boundaries and limitations below, not a claim that complete analysis is impossible.

## Identity, owning symbols, and dependency direction

**Protocol facts:** LSP 3.17 document symbols contain names, kinds, enclosing/selection ranges, and optional children; references return locations for a symbol at a document position. These are navigation results. Optional monikers add scheme-scoped identifiers with declared uniqueness, rather than source revision identity. Document versions track individual document changes; a references response does not identify an atomic project/configuration capture. **Inference:** request ordering or a document version alone cannot bind every dependency read. [Document symbols](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#documentSymbol), [references](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_references), [monikers](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_moniker), [document versions](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#versionedTextDocumentIdentifier)

**Recommendation:** derive the owning symbol from captured syntax: nearest enclosing function/method, otherwise the top-level declaration. Attach captured source/configuration identity to every symbol handle and range. Re-identify after edits; a name, position, moniker, or pointer alone cannot authorize a write against different bytes. A rename or move requires fresh analysis of old and new declarations, references, and namespace membership; never silently carry the former range forward. This follows the position-based protocol and package-relative identity boundaries, rather than a tool-provided revision guarantee.

**Rust facts:** native `AnalysisHost` applies changes and returns analysis snapshots; advancing it cancels outstanding analyses. HIR belongs to a particular crate instance and cfg configuration. [Snapshot/cancellation](https://github.com/rust-lang/rust-analyzer/blob/03fcb77246f2568adb0e9b2fa60d19c6cc1686f4/crates/ide/src/lib.rs#L192-L241), [crate instances](https://github.com/rust-lang/rust-analyzer/blob/03fcb77246f2568adb0e9b2fa60d19c6cc1686f4/docs/book/src/contributing/architecture.md#L173-L178) rustc's internal `DefPathHash` is stable across compilation sessions for a definition path; its crate part incorporates crate name and metadata. **Inference:** that is useful correspondence, not a content revision or identity preserved through arbitrary renaming/moving. [Pinned identity source](https://github.com/rust-lang/rust/blob/1.90.0/compiler/rustc_span/src/def_id.rs#L52-L57), [crate identity](https://github.com/rust-lang/rust/blob/1.90.0/compiler/rustc_span/src/def_id.rs#L132-L174)

**Go facts:** each `packages.Load` has a consistent type universe; objects/types from different loads must not be mixed. `objectpath` communicates package-relative object identity between processes; paths omit package identity and may have multiple encodings. Locals and `init` functions are among unsupported objects. **Recommendation:** include package variant plus capture identity; rebuild correspondence after structural changes and use syntax owners for objects without paths. [Load identity](https://github.com/golang/tools/blob/v0.37.0/go/packages/packages.go#L244-L250), [objectpath](https://github.com/golang/tools/blob/v0.37.0/go/types/objectpath/objectpath.go#L5-L43), [limits](https://github.com/golang/tools/blob/v0.37.0/go/types/objectpath/objectpath.go#L177-L207)

**Inference/recommendation:** distinguish `A → B` (A relies on B) from reverse dependents of B. Forward edges describe prerequisites; reverse traversal identifies potentially affected owners. A reference result needs mapping from each occurrence to its owner before becoming an edge. Calls alone omit type, constant, field, import, trait/interface, and initialization dependencies. Build typed edges and invert them over the captured analysis universe; do not equate a reference query with exhaustive closure. Traverse transitively to a fixed point, retaining cycles. A depth/resource cap must trigger widening, never silently truncate. Use the union of pre-edit and candidate evidence, since changed resolution can introduce edges absent from the old graph. Declared dependencies can only enlarge this related scope.

Two concrete warnings substantiate this distinction. rust-analyzer's reference operation can filter imports/tests and, depending on cursor position, return only constructor uses of a type. gopls searches direct reverse imports for package-level objects but transitive reverse imports for fields/methods, expands interface satisfaction, and documents a potential miss caused by skipped non-workspace expansion. [Rust search](https://github.com/rust-lang/rust-analyzer/blob/03fcb77246f2568adb0e9b2fa60d19c6cc1686f4/crates/ide/src/references.rs#L99-L149), [Go search](https://github.com/golang/tools/blob/gopls/v0.20.0/gopls/internal/golang/references.go#L287-L352) rustc's incremental DAG records compiler query reads, not an exported source-symbol graph. Translating it to coordination owners would itself require research. [Compiler DAG](https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation.html)

## Incomplete code and configuration limits

**Rust facts:** rust-analyzer parsing returns a tree plus errors and aims to remain partially available during broken builds. This supports navigation during unfinished editing; it does not certify complete resolved dependencies. [Parser and reload invariants](https://github.com/rust-lang/rust-analyzer/blob/03fcb77246f2568adb0e9b2fa60d19c6cc1686f4/docs/book/src/contributing/architecture.md#L72-L88), [broken builds](https://github.com/rust-lang/rust-analyzer/blob/03fcb77246f2568adb0e9b2fa60d19c6cc1686f4/docs/book/src/contributing/architecture.md#L249-L255) Build-script execution, features, target, cfg, and proc-macro expansion are configurable; rebuild-on-save is explicitly tied to saved script/macro changes. **Inference:** unsaved source and previously built expansion inputs can diverge. [Pinned settings](https://github.com/rust-lang/rust-analyzer/blob/03fcb77246f2568adb0e9b2fa60d19c6cc1686f4/docs/book/src/configuration_generated.md#L59-L167), [proc macros](https://github.com/rust-lang/rust-analyzer/blob/03fcb77246f2568adb0e9b2fa60d19c6cc1686f4/docs/book/src/configuration_generated.md#L1338-L1358)

Cargo scripts generate files and influence cfg/environment; procedural macros execute code with compiler file access and produce syntax. **Recommendation:** include macro definitions, invocations, expansions, generated inputs, manifests/lock/config files, compiler/sysroot, and relevant environment in the captured analysis basis. Failed/unavailable expansion or unknown generated provenance requires affected crate/package scope and its reverse dependents. Uncaptured external reads can invalidate analysis altogether; widening source files cannot repair that. [Build scripts](https://doc.rust-lang.org/cargo/reference/build-scripts.html), [procedural macros](https://doc.rust-lang.org/reference/procedural-macros.html)

**Go facts:** `Info` may be incomplete on type errors and omits invalid expressions. `Load` may succeed while packages contain errors or missing syntax. Overlays replace selected source contents, but external drivers vary in support. `Tests=true` loads distinct test variants; `CompiledGoFiles` can differ from original Go files after preprocessing. [Partial info](https://github.com/golang/go/blob/go1.25.0/src/go/types/api.go#L208-L266), [load errors/overlays/variants](https://github.com/golang/tools/blob/v0.37.0/go/packages/packages.go#L205-L260), [compiled inputs](https://github.com/golang/tools/blob/v0.37.0/go/packages/packages.go#L447-L456) Therefore checking only `Load`'s returned error is insufficient.

gopls references use the selected file's build configuration, not all builds; arbitrary user tags are not inferred, and cross-target analysis can disable cgo. [Workspace limits](https://go.dev/gopls/workspace) `go generate` explicitly runs arbitrary processes and is not automatically invoked by builds/tests. **Recommendation:** capture generated files as ordinary inputs, preserve their provenance, record modules/workspace files, toolchain, environment, tags, cgo inputs and test variants; union required configuration scopes or widen. No single platform query establishes repository-wide completeness. [Pinned generate command](https://github.com/golang/go/blob/go1.25.0/src/cmd/go/internal/generate/generate.go#L34-L58)

## Freshness and conservative fallback

These are **Falinks recommendations**, grounded in the capture and incompleteness limits above:

1. Bind analysis to exact captured bytes, file membership, project metadata, dependency/generated artifacts, configuration, and tool versions. An overlay over otherwise mutable disk is insufficient. New declarations can change resolution even without an old edge: namespace changes invalidate the relevant file/package and dependents. Maintain separate analysis validity and symbol correspondence; canceled, stale, missing, or inconsistent evidence cannot narrow scope. Changed captures require recomputation or a demonstrated invalidation rule before reusing evidence.
2. Prefer owning symbol, then a demonstrated related affected set. Syntax-owner uncertainty widens to file; resolution/type/macro/config uncertainty widens to package/crate plus affected reverse package/crate closure. Shared imports, type/trait/interface changes, initialization, and rename/move generally cross owners. Unknown workspace membership or external environment disables independent-symbol acceptance until recapture or a broader bounded input universe is available. Package-local fallback alone cannot bound cross-package effects.
3. Treat **input freshness** and **output mutation footprint** separately. A whole-file formatter reads/writes the entire file even when invoked for one function; a package generator may read many files and rewrite several outputs. Run on temporary captured inputs. At completion, atomically verify every captured input/config precondition and all output destinations, then apply the coordinated output group all-or-none; retain outputs on rejection. Hold coordination only for check-and-apply, never the command lifetime. A small textual diff does not shrink the command's read assumptions.
4. Different functions in one file may have distinct owners, yet shared imports, inferred types, macros, and command footprints can relate them. Independent application requires verified owner mapping, sufficient dependency/invalidation evidence, and a patch precondition that preserves concurrent sibling edits despite shifted offsets. Whole-file revision rejection is a conservative implementation; it demonstrates stale-file protection, not independent-symbol application. Compiler evidence cannot cover arbitrary behavioral coupling through runtime state, reflection/FFI, or external resources.

## NEXT: one short-session capture and owner probe

Use provisional rust-analyzer LSP and public Go `packages`/`types` on tiny immutable captured workspaces; no Rust embedding or engine integration. Per language, include two unrelated sibling functions, a callee/caller across files, one unfinished parse/type edit, and one cfg/build-tag change. Pin executables, host/target, configurations, capabilities, query positions, and exclusions. Save one runnable fixture command and an evidence table recording input/config hashes, query binding, owner identities/ranges, direct forward/reverse evidence, diagnostics, and required fallback.

Insert text before the second sibling and reanalyze a new capture: require correct owner correspondence and shifted ranges. Change the callee/configuration or introduce broken source: require old evidence to be identified as stale and uncertain scope widened. A successful first probe demonstrates these bounded query/ownership facts; it does **not** establish independent-symbol application or exhaustive closure. Later gates must cover trait/interface/inference, rename/move, macro/generated provenance, configuration unions, and actual preservation of both concurrent sibling edits. Controlled formatter/generator freshness and atomic output application remain separate coordination work. Whole-file revision checks alone remain insufficient. This probe neither establishes behavioral correctness nor selects production integration.
